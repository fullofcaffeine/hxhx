# Second-pass review: checked generated plugin text

## Practical result under review

The generated native-plugin entry now proves that its call to
`HxHxBackendPluginHost.register_provider_type` came from one Haxe-authored
plan. The compiler performs this check before it writes the OCaml file.

For example, the successful file still contains this call:

```ocaml
HxHxBackendPluginHost.register_provider_type "test.plugin" "backend.js.JsBackend"
```

The generator now builds that line from ordinary text and one checked
placeholder. A placeholder carries the expected use identity, plan revision,
exact OCaml symbol, active profile, and runtime requirement.

This task migrates one production path. The inventory still contains 444
unchecked private-runtime references. Sixteen of those references are in
generated text.

## Independent behavior sources

The existing M13 plugin-layout fixture owns the generated file and native Dune
build contract. The Full1 upstream-to-`hxhx` fixture owns the real host
boundary. It builds the plugin with upstream Haxe, loads it in `hxhx`, selects
the registered provider, and runs the generated JavaScript.

These fixtures existed before this checker. They do not use the checker to
create their expected results.

## Architecture review

- The Dune emitter records the plugin-host runtime requirement only when it
  emits a real plugin registration entry.
- The requirement names the exact generated module, compiler decision,
  capability, portable profile, and `HxHxBackendPluginHost` runtime root.
- The checked builder consumes one generated-text occurrence. It then checks
  identity, order, count, profile, requirement, and exact symbol.
- The builder scans the complete generated file. It ignores OCaml strings and
  nested comments, but it rejects private `Hx...` names in unchecked code.
- The output record stores exact bytes and a SHA-256 content hash. The Dune
  emitter checks that hash again immediately before it saves the file.
- The successful generated bytes did not change. The adapter contains no
  target lowering, printer repair, or handwritten compiler semantics.

## Challenge findings and disposition

The first checker draft used predictable marker identifiers while it inspected
the complete file. An unchecked literal could spell the same marker. That
literal could imitate the proof for a real placeholder hidden inside a string.

The final checker reserves its marker namespace in literal OCaml code. It also
inserts a separator while it scans literal chunks, so text on both sides of a
real placeholder cannot form a forged marker. The focused fixture reproduces
this case and now rejects it.

The focused fixture also rejects a portable-only plugin requirement in the
metal profile. It rejects a use owned by a different generated file. The output
record returns a copy of its use-ID list, so callers cannot change the stored
order through the public getter.

## Review conclusion

The implementation follows the accepted parent architecture. Haxe code owns
the decision and the exact private-runtime occurrence. The text builder only
checks and renders that decision.

The `thinking:xhigh` level was sufficient. Another Oracle request is not
