# Second-pass review: Array indexed searches

## Outcome

The change is safe to close as a two-method hard cut. Final typed calls to
`Array.indexOf` and `Array.lastIndexOf` now carry their exact argument form,
element type, integer result, source order, and runtime function into OCaml
syntax. The two old source-method branches were removed from the late builder.

## Optional argument forms

An installed Haxe 4.3.7 typed-AST probe established three distinct inputs:

- an omitted start produces a one-argument call;
- explicit `null` produces a two-argument call whose second type is
  `Null<Int>`;
- an explicit integer produces a two-argument call whose second type is
  `Int`.

The closed plan therefore has separate omitted-start operations. Supplied
starts accept only the typed `Int` or `Null<Int>` forms. Omitted starts select
small `HxArray` wrappers, so `lastIndexOf` can read the already-evaluated
receiver's length without evaluating the Haxe receiver expression twice.

Focused corruption cases replace the supplied start with `Float` and replace
an omitted-start runtime function with the supplied-start function. Both are
rejected before syntax generation. Existing common validation also checks the
root `Array<T>` owner, operation, source field, arity, result, schedule,
runtime requirement, profile, revision, and occurrence identity.

## Runtime behavior and identity

The shared Haxe 4.3.7/generated-OCaml tracer covers omitted, explicit-null,
positive, negative, excessively negative, and oversized starts; missing
values; empty arrays; and object identity. It also records
`receiver,value,start` order and proves each source expression runs once.

The tracer found two real pre-existing runtime mismatches:

1. explicit `null` reached handwritten OCaml as the Haxe null sentinel, while
   the search functions incorrectly required an OCaml `int`;
2. an excessively negative `lastIndexOf` start returned `-1`, while the
   installed Haxe 4.3.7 oracle clamps the derived start to index zero.

The runtime boundary now accepts the optional carrier polymorphically, checks
for the null sentinel immediately, and returns a concrete `int`. No untyped
value enters search logic. The negative-start normalization now matches the
measured upstream behavior. The object checks confirm that Array search uses
Haxe object identity rather than structural equality.

## Runtime authority, reports, and inventory

The Haxe-authored plan owns when each private `HxArray` primitive is used.
Handwritten OCaml continues to own only Array storage and search behavior; it
does not inspect Haxe source, choose a compiler operation, or repair generated
output.

The function-plan revision is `v91`, the call-boundary model is `v25`, the
standard Array proof is `v5`, and the lowering schema is 76. The inspection
reader and its independent JavaScript consumer validate the new operations and
runtime names. Six deterministic reports were regenerated by the repository
updater and then passed an ordinary comparison run.

The private-runtime inventory falls from 341 to 338. Two removed rows are the
late `indexOf` and `lastIndexOf` calls. The third is the late `HxArray.length`
reference that previously recomputed a default `lastIndexOf` start and could
evaluate the receiver twice.

## Claim boundary

No generated OCaml was edited. Runtime source-selection authority and README
Goals did not move. Requirements-only runtime selection remains incomplete,
with 338 private-reference inventory entries still open.

Oracle review was deliberately skipped. The standard Array seam was already
accepted, the installed Haxe 4.3.7 compiler supplied a direct behavior oracle,
and focused, vertical, inspection, corruption, inventory, and deterministic
report evidence converged without an unresolved architecture decision.
